# AGENTS.md

A concise guide for AI coding agents working on this repository. It complements `README.md` with machine-actionable build, test, run, and convention notes.

## This repository is public

Everything committed here is world-readable and permanent — source, comments, tests, docs, commit messages, PR titles and descriptions, issue text. A later fix does not retract what has already been cloned, cached or indexed. This file is public too, and is bound by its own rules.

Using an internal source to get the behaviour right is fine; publishing it is not. Only the externally observable result belongs in the repo.

- **Never name private repositories or services.** `desksdkgo`, `twapi-go-sdk` and the MCP SDK are public and may be cited freely. The backends behind the Projects and Desk APIs are not — do not name their repositories, packages, files, handlers, models, or query-argument identifiers. Describe the HTTP endpoint instead: route, parameters, JSON keys, status codes.
- **Never name internal infrastructure.** Deployments, hostnames, dashboards, monitoring, CI tooling, chat channels, wikis, runbooks, or environment detail beyond the documented `TW_MCP_ENV` values.
- **Never reference internal tracking.** Ticket keys, incident IDs, or links and commit hashes in private repositories. Public protocol references (`SEP-2575`) are fine — those are published.
- **Never describe a backend defect as a defect.** State what the endpoint does today ("list endpoints clamp `pageSize` over 100 to 100"), not that it is a bug, what causes it, or when it is due to be fixed — the service is still running the old code.
- **Never publish unreleased information.** Roadmap items, planned deprecations, dated fixes, feature flags, or capacity and traffic figures.
- **Never commit real data.** Tokens, API keys, cookies, real installation subdomains, or real customer and employee names, emails and IDs — in code, tests, fixtures, log samples and error strings alike. Fixtures use `example.com`, `test.teamwork.com`, `john@example.com`, and IDs like `777`/`12345`.

| Instead of                                          | Write                                                        |
|-----------------------------------------------------|--------------------------------------------------------------|
| "bound by `Model.UnmarshalParam` in `<private repo>`" | "the endpoint parses `YYYY-MM-DD` only, and 400s otherwise"   |
| "clamped in the backend's request-defaults helper"   | "list endpoints clamp `pageSize` over 100 to 100"            |
| "broken until the next backend release"              | "returns 422 in this case"                                   |
| "see PROJ-1234"                                      | omit, or describe the behaviour the change addresses         |
| a real site URL in a test                            | `https://test.teamwork.com`                                  |

Commit messages and PR descriptions follow the same rules: what the change does and why, in terms of the public API and this server's own behaviour. No internal links, no ticket keys, no "as discussed in <channel>", no private reviewer names. Before committing, re-read the diff as an outsider would and drop any line that only makes sense to someone with access to private systems — the code ships, the reference does not.

## Project overview
- Language/runtime: Go 1.27 or newer
- Purpose: Model Context Protocol (MCP) server for Teamwork.com with HTTP, STDIO transports and HTTP CLI.
- Main entry points:
  - STDIO server: `cmd/mcp-stdio/main.go`
  - HTTP server: `cmd/mcp-http/main.go`
  - HTTP CLI (tester): `cmd/mcp-http-cli/main.go`
- Core domain/tooling: `internal/twprojects` (tools for projects, tasks, users, tags, comments, milestones, timers, timelogs, etc.)
- Layout: `pkg/` is the shared, importable base (other MCP servers depend on it); `internal/` is this server's own tool surface. See "`pkg/` is a published API" below before moving code between them.

## Setup commands
- Install Go toolchain: Go 1.27 or newer (module declares `go 1.27.0`).
- Sync deps: `go mod download`
- Lint/format (optional but recommended):
  - Format: `gofmt -s -w .`
  - Vet: `go vet ./...`
  - Install `golangci-lint` and run `golangci-lint -c .golangci.yml run ./...` for more checks.

## Build and run
- STDIO server (local, safest for editor/desktop agents):
  - Env: `TW_MCP_BEARER_TOKEN=<token>`
  - Run: `go run cmd/mcp-stdio/main.go`
  - Flags: `-read-only` to restrict writes, `-toolsets=<comma-separated>` to limit exposed tools.
- HTTP server (for hosted/cloud or tools that only speak HTTP):
  - Env (examples): `TW_MCP_SERVER_ADDRESS=:8080`, optional `TW_MCP_LOG_LEVEL=debug`
  - Run: `go run cmd/mcp-http/main.go`
  - Health: GET `/health`
- HTTP CLI (for quick tests against HTTP server):
  - List tools: `go run cmd/mcp-http-cli/main.go -mcp-url=<url> -mcp-token=<token> list-tools`
  - Call tool: `go run cmd/mcp-http-cli/main.go -mcp-url=<url> -mcp-token=<token> call-tool <toolName> '{"k":"v"}'`
- Handler walkthrough against a live site (creates and deletes real data):
  - Env: `TWAPI_SERVER`, `TWAPI_TOKEN`, `PROJECT_ID` (same vars as `go test`), each overridable by a flag
  - Run: `go run ./cmd/mcp-test [-suite=all] [-step] [-keep]`
  - Suites live one per file and register in `suiteRegistry`; see `cmd/mcp-test/README.md`.
- Next release version (what the `Release` workflow computes on a dispatch):
  - Run: `GH_TOKEN=$(gh auth token) go run ./cmd/next-version`
  - Flags: `-bump=auto|patch|minor|major`, `-from=<tag>`, `-to=<rev>`, `-no-pr-lookup` (subject-only, no API calls)
  - Without a token it falls back to commit subjects and says so; see `cmd/next-version/README.md`.
- Docker (optional, for image builds):
  - Requires Docker Buildx. Local load: `make build` or `make build-stdio`
  - Multi-arch push (maintainers): `make push` or `make push-stdio`

## Testing instructions
- Run all tests: `go test ./...`
- Focus a package: `go test ./internal/twprojects`
- Run a single test: `go test ./internal/twprojects -run TestName`
- Notes:
  - Tests in `internal/twprojects` mock the Teamwork API via an in-memory `twapi.Engine` stub (`mcpServerMock` in `internal/twprojects/main_test.go`). No external services are required.
  - Keep tests fast and hermetic. Add/update tests alongside any tool changes.

### Test file naming
Tests live in standalone `_test.go` files, and **every test file must be named
after an existing non-test `.go` file in the same directory**: `tasks.go` is
tested by `tasks_test.go`, and by `tasks_{suffix}_test.go` when one file is not
enough. A `{suffix}_test.go` with no `{suffix}.go` beside it is wrong — name it
after the code under test, not after the scenario. A suite that spans a whole
package hangs off the file that owns the surface it checks, usually `tools.go`.

```
tickets.go   → tickets_test.go, tools_error_test.go        ✅
             → schema_validation_test.go                   ❌ (no schema_validation.go)
```

`main_test.go` is the one exception, since Go's `TestMain` and the shared
fixtures have no source file of their own — keep it to setup, and move any
package-wide suite into its own `main_{suffix}_test.go`.

## `pkg/` is a published API; `internal/` is not

This repo is the shared base for other Teamwork MCP servers, which are separate modules and may be private. Go's internal rule is path-based, not visibility-based: a package under `internal/` cannot be imported from another module at all, whatever that module's permissions. So the split is load-bearing, not stylistic.

- **`pkg/`** — anything a second server needs: `toolsets` (the tool framework), `helpers` (schemas, param binders, sparse fields, `HandleAPIError`), `config` (startup, `NewMCPServer`, middleware), `auth`, `request`, `network`, `presigned`, `logsafe`, `twctx` (per-request bearer-token values), `cli` (the `-toolsets` flag), `testutil` (product-neutral mocks).
- **`internal/`** — this server's own surface: `twprojects`, `twdesk`, `twspaces`, `twchat`, the profile/tool-order policy in `internal/cli`, and the group wiring in `internal/testutil`.

Rules that follow from this:

- **Nothing in `pkg/` may import `internal/`,** tests included. It compiles inside this module and breaks every other consumer, so `depguard` in `.golangci.yml` rejects it — verify a change to that rule still fires by adding a violating import, since a rule matching nothing also reports zero issues. When a shared helper's own test needs product wiring, the wiring is on the wrong side of the line.
- **Nothing in `pkg/` may name a product.** A `twprojects`-shaped parameter or a hardcoded `"twdesk"` prefix is a product decision; pass it in. `pkg/helpers` referencing `projects.LegacyNumber` as a *type constraint* is fine — that is the public SDK, not this repo's tool packages.
- **A behaviour that varies per server is a parameter, not a constant.** `config.Load` takes `Option`s for this: `WithEnvPrefix` (defaults to `TW_MCP_`), `WithServerIdentity` (the name and title in the initialize handshake), `WithProfiles`. Adding a new setting means adding it to `newResources` under `env(...)`, never `getEnv(...)` — the bare form exists only for the `DD_*` variables, whose names the Datadog agent owns. `TestNewResourcesEnvPrefix` and `TestNewResourcesDatadogEnvIsNotPrefixed` pin both halves.
- **Renaming or moving anything under `pkg/` is a breaking change** for the servers built on it, and `cmd/next-version` reads the PR title to pick the bump. Treat it as `Feature!:` or carry a `BREAKING CHANGE:` body.
- Changing `pkg/config.Version`'s import path breaks the release: it is set by `-ldflags` in `Dockerfile` and `.github/workflows/release.yaml`, and a stale path fails silently, leaving every binary reporting `dev`.

## Toolset namespaces and OAuth scopes
- Every `ToolsetGroup` declares its tool-name prefix and OAuth scope with `SetNamespace("twprojects", "projects")`. Two things read it: the `tools/list` scope filter in `pkg/config/config.go`, and the `scopes_supported` advertised in the RFC 9728 protected-resource metadata, which `cmd/mcp-http` derives with `toolsets.Scopes(groups)`. Neither is written out by hand any more — a group added with a scope nobody advertised would have its tools filtered out for every token, and a group that declares no namespace at all is **never filtered**, so its tools go to every caller regardless of scope. `TestEveryGroupDeclaresItsNamespace` in `cmd/docs-gen/main_test.go` fails when a product forgets.
- The filter matches the whole `<prefix>-` segment, not a raw string prefix, because namespaces are free to be prefixes of one another: a `twpro` namespace would otherwise swallow every `twprojects-` tool and hand it out under the wrong scope. `TestListToolsFiltersByGroupNamespace` in `pkg/config/config_scopes_test.go` covers this with exactly that pair; `TestNamespacesDoNotShadowEachOther` rejects two products sharing one.
- One group per namespace. A group is the unit a scope applies to, so tools from two namespaces in one group cannot be filtered apart.

## Code layout and conventions
- The `twprojects-planning` sub-toolset holds the resource-scheduler allocation tools and `users_workload`. They are the two planes of resource planning — allocated time and estimated task time — and are deliberately **not summed**; `users_workload` was moved out of `twprojects-people` when the allocation tools landed, so anyone pinning `-toolsets=twprojects-people` has to add `twprojects-planning` to keep it.
- Tool surface lives in `internal/twprojects/*.go`. Files are organized by resource (e.g., `tasks.go`, `projects.go`) with matching `*_test.go`.
- Tools are registered in `internal/twprojects/tools.go` via `DefaultToolsetGroup(readOnly, allowDelete, engine)`.
  - Read-only enforcement is centralized; writes go in `AddWriteTools(...)`, reads in `AddReadTools(...)`.
  - Destructive operations (delete) are guarded by the `allowDelete` flag; keep this pattern intact.
- Prefer clear, explicit parameter schemas for tools and consistent naming:
  - Tool names use the `twprojects-<action>` convention as exposed to MCP clients (see the existing tools for examples).
- Follow standard Go style: keep functions small, pass `context.Context`, check and wrap errors, and ensure deterministic tests.

## Adding or modifying tools (quick checklist)
- Implement the tool function in the appropriate file under `internal/twprojects/` and return a `server.ServerTool` (see existing patterns, e.g., create/update/get/list functions in each file).
- Register it in `DefaultToolsetGroup(...)`:
  - Read-only tools → `AddReadTools(...)`
  - Write tools → `AddWriteTools(...)` (and behind `allowDelete` for deletes)
- Add tests in the matching `*_test.go` file using `mcpServerMock(...)` and `toolRequest` helpers found in `internal/twprojects/main_test.go`.
- A tool that advertises a parameter needs a test that asserts the parameter reaches the wire, not just that the call succeeds: the mocks reply with the same canned body either way, so a silently dropped filter or page argument looks identical to a working one. Use `testutil.ProjectsMCPServerMockWithRequestURL` / `testutil.DeskMCPServerMockWithRequestURL` (or the `...WithRequestBody` variants for writes) to assert the query string, and `testutil.DeskMCPServerMockWithRequest` when the HTTP method is what distinguishes two tools (`twdesk-link_task_to_ticket` and `twdesk-unlink_task_from_ticket` share a path and differ only in POST versus DELETE). `twdesk-search_tickets` shipped ignoring page, pageSize, orderBy, orderDirection and fields for exactly this reason.
- A parameter in a tool's `InputSchema` that no binder in the handler names is accepted and silently dropped: the SDK validates the schema, not the handler, so the caller is told the value was applied when nothing reached the wire. `TestEveryToolParameterIsBound` in `internal/twprojects/tools_params_test.go` parses the package and fails on one — it caught `project_id`/`task_id` on `update_timelog`, `project_id` on `update_message` and `parent_team_id` on `update_team`, each copied from the matching create tool onto an SDK update request that had no such field. A parameter read out of the raw arguments map instead of through `helpers.ParamGroup` (`notify` via `parseNotify`, `order_by` via `ordering.param`) belongs in that test's `indirectlyBoundParams` map, keyed by the helper that reads it.
- Moving a timelog is `project_id`, `task_id` and `clear_task` on `twprojects-update_timelog`, and the three are not independent: the update endpoint derives the project from the task whenever the timelog ends up with one, so a `projectId` sent for a timelog that is still on a task is ignored. `clear_task` is what detaches it, through the SDK's tri-state `TaskID` (`twapi.NullInt64()`), and the field is tagged `omitzero` because an unset value encoded as `null` would detach the task on every unrelated update. `TestTimelogUpdateMoveReachesTheWire` pins all three states on the request body.
- `group_by` on `twprojects-summarize_timelogs` picks the time report's dimension (`GET /projects/api/v3/time/report/{type}.json`), and a `task` row is not comparable to a `project` one: it carries no time logged directly on a project, and grouping is per task ID, so a parent excludes its subtasks. Nothing in the response shows either, hence the warning in the tool description. `task` also needs `reportType=loggedtime` — the default variant returns every task carrying an estimate as a row of zeros. `TestSummarizeTimelogsGroupByReachesTheWire` pins path, `type`, `reportType`, `include` and `fields[...]` for all three dimensions. Row names need the SDK's typed `Included` map per entity (`Included.Tasks`, twapi-go-sdk v1.26.1+).
- `parent_team_id` on `twprojects-update_team` reaches a v1 route that reads a missing value as "leave the hierarchy alone" and `0` as "move to the top level", so the SDK field is a `*int64` and the tool must not default it. The route answers 404 when the parent is the team's own ID. `TestTeamUpdateParentReachesTheWire` pins the omitted, set and zero cases.
- A message cannot change project through `twprojects-update_message`: the update route takes the title, body, category, privacy and notification fields only, and reads the project from the stored message. Moving one is a separate route (`PUT /messages/{id}/move.json`, taking `projectId` plus `moveFiles`/`copyFiles`) that neither the SDK nor this server exposes yet.
- Desk SDK gotcha: `desksdkgo`'s `client.Tickets.Search` builds its query solely from the qs-encoded `SearchTicketsFilter`, which carries no pagination, ordering or sparse-fieldset field — anything you set outside the struct is discarded. `internal/twdesk/tickets.go` therefore reaches `/search/tickets.json` through `deskclient.NewService[...]` plus `NewDefaultPathHandler("search/tickets")`, which takes a `url.Values` the handler controls. Check any `<Action><Model>Filter` struct for the params you need before routing a tool through its bespoke SDK method.
- A tool handler never returns a raw Go error for something the API answered. Every API call goes through `helpers.HandleAPIError(err, "failed to …")`, which turns a status the caller can act on into an `IsError` tool result; a raw error becomes a protocol-level error instead, so the model sees a transport failure with no status to read and none of the handler's wrapped message. Local faults are tool results too, via `helpers.NewToolResultTextError(...)` — bad caller input (malformed base64 in `twdesk-create_file`) as much as an encode failure. `TestAPIFailuresAreToolResults` in `internal/twdesk/tools_error_test.go` drives representative Desk tools against 403/404/500 mocks and fails on a Go error before its assertion runs.
- `HandleAPIError` reads the status out of the Desk SDK's *message text*, because `desksdkgo` declares no error type at all: every non-2xx response leaves it as a bare `fmt.Errorf("unexpected status code: %d", …)` (`client/resource.go`, `tickets.go`, `helpdocarticles.go`) or `"failed to upload file, status code: %d, …"` (`Files.Upload`). Without that parse the typed-`*twapi.HTTPError` branch misses and every Desk failure falls through to the raw-error return — so calling `HandleAPIError` in a Desk handler is only load-bearing while `deskStatusCodePattern` in `pkg/helpers/error.go` still matches. If a Desk SDK bump introduces a real error type, switch to `errors.AsType` on it and drop the pattern. `TestHandleAPIError` in `pkg/helpers/error_test.go` pins both SDKs' shapes, plus that an error carrying no status stays a Go error.
- Desk pages are smaller than v3's, so Desk tools use the local `pageSizeSchema()` / `searchPageSizeSchema()` in `internal/twdesk/meta.go`, never `helpers.PageSizeSchema()` (500, the v3 limit). Desk rewrites an oversized page instead of rejecting it: list endpoints clamp over 100 down to 100, and the search endpoints reset anything over 200 back to 50, so asking for 250 returns fewer rows than asking for 200 and the response says nothing about it. `TestPageSizeCeilingsMatchTheAPI` and `TestNoToolAdvertisesAnUnreachablePage` in `internal/twdesk/meta_test.go` guard both ceilings.
- Desk query-string dates are `YYYY-MM-DD` only. A query parameter is parsed with that one layout; request *bodies* accept RFC 3339, but that does not carry over, so a timestamp on a GET is rejected with 400 before the endpoint runs. `desksdkgo` models `SearchTicketsFilter.StartDate`/`.EndDate` as `*time.Time`, and qs renders those as RFC 3339 — set them on the `url.Values` yourself instead. Do not add `helpers.EndOfDay()` to the upper bound: the search endpoint already widens `startDate` to the start of its day and `endDate` to the end of its, then filters `createdAt` on that range.
- Moving a task between tasklists carries its subtasks and detaches an invalidated parent, both server-side. `PUT /projects/api/v3/tasks/{id}.json` (the SDK's `TaskUpdate`, behind `twprojects-update_task`) moves the whole subtree, then drops the moved task's own parent link when that parent is not in the destination. Only a parent the payload *inherited* is dropped — one the caller sent is still validated, so passing `parent_task_id` alongside a `tasklist_id` change fails with "parent task is in another list". Do not send one when moving. This arrived in an API fix in 2026-08; before it, v3 moved only the named task and stranded the subtree, which is why the client used to move each descendant by hand. `twprojects-move_tasks` is now a loop of task updates, and exists to batch several subtrees into one tool call — it skips a task already carried by another, since a descendant listed before its ancestor would otherwise be detached.
- Clearing a task's parent needs the `0` sentinel, not `null`. `parentTaskId: 0` detaches a subtask; `null` is a no-op, because `null` means "not provided" for every optional parameter in this repo. Commit `be42c41` added `{Type: "null"}` to every optional param so OpenAI strict-mode clients, which must send every property, can fill the unset ones — so repurposing `null` as "clear" would detach subtasks on any unrelated update those clients make. Fields that need clearing get an explicit boolean instead: `clear_assignees`, `clear_parent_task`. `TestTaskUpdateNullParentTaskIDIsNotAClear` pins the null semantics.
- The MCP SDK validates a tool's `InputSchema` before the handler runs, so a parameter listed in `Required` can never be defaulted or aliased in Go. Widening a shipped tool's parameter while still accepting the old form (as `move_task_to_workflow_stage` does for the scalar `task_id` it advertised before it took `task_ids`) means leaving the new parameter out of `Required` and enforcing it in the handler.
- Annotation hints are mandatory and must be explicit: every tool sets `ReadOnlyHint`, `DestructiveHint` and `OpenWorldHint`. The latter two are `*bool` in the SDK, so a nil value is omitted from `tools/list` and the spec then defaults it to `true`; OpenAI's app review rejects tools with missing hints. Use `new(false)` unless the tool truly destroys data (deletes, plus Desk ticket create/reply, which email the customer) or reaches outside the customer's Teamwork account (help-doc articles published to a public knowledge base, Desk ticket create/reply). `TestAnnotationHintsAreExplicit` in `cmd/docs-gen/main_test.go` guards this across all four products with `allowDelete=true`.
- JSON-Schema gotcha (OpenAI Responses API): every `Type: "array"` node — including inside `AnyOf`/`OneOf`/`AllOf` branches — must declare `Items`. OpenAI rejects bare arrays at tool-registration time even with `strict: false`; Anthropic does not, so Claude Desktop hides the bug. `TestToolInputSchemasArrayItems` in `internal/twprojects/tools_test.go` guards this — if it fires, pick the right item schema rather than weakening the test.
- Any output schema built by reflection over an SDK response must be generated through `helpers.WithDateTypeSchema(...)`. `twapi.Date` and `twapi.OptionalDateTime` are defined over `time.Time`, so `jsonschema.For` describes them by `time.Time`'s unexported fields — an opaque `object` — while their `MarshalJSON` writes a string. Every response carrying one then fails output-schema validation at any validating client, on every call, for every row; non-validating clients see nothing wrong, so this ships silently. A response picks the types up transitively (`projects.Team` is the only model with an `OptionalDateTime`, but `SearchResponse` sideloads `Team`), so register the override rather than reasoning about which models are affected — pre-existing `TypeSchemas` entries are preserved, as `teams.go` does for `LegacyNumber`. Two traps when testing: the mocks in `*_test.go` usually reply `{}`, which leaves such fields nil and encodes as `null`, exercising neither the set nor the unset case; and neither the server nor `testutil.ExecuteToolRequest` validates structured content, so a mismatch is invisible in-process. `TestTeamDeletedDateValidatesAgainstOutputSchema` in `internal/twprojects/teams_test.go` validates the result against the tool's published schema by hand — copy that shape rather than assuming a green tool test means the wire shape is right.
  - The override declares a `format`, and **declaring the type is not enough on a raw-streamed body.** The v1 routes spell "unset" as an empty string, so `deletedDate: ""` reaches the caller verbatim on `list_teams` — `ExecuteRaw` means `MarshalJSON` never runs to turn it into `null`, which is why the SDK's own `OptionalDateTime` fix could not reach it. `""` is a valid `string` but not a valid `date-time`, so widening the declared type leaves a format the body still violates. Run any raw body carrying such a field through `helpers.NullifyEmptyDates(body, "<field>")` before returning it.
  - `jsonschema-go` treats `format` as an annotation and **never asserts it** — there is no option to turn it on — so `Validate` passes a body that a client running Ajv-with-formats rejects outright. A test that only calls `Validate` is blind to exactly this half; `checkSchemaFormats` in `teams_test.go` walks the schema alongside the value and parses every string under a `date`/`date-time` node. Assert both halves, or the next mismatch ships green.
- Date and date-time parameters go through the binders in `pkg/helpers/tool_parser.go`, which accept more than one layout (see `dateTimeLayouts` in `pkg/helpers/datetime.go`): RFC 3339, an offset-less date-time, and a plain `YYYY-MM-DD`. Models emit the plain date by default when asked about a range, so a strict RFC 3339 parse costs a failed first call and a visible retry. Do not narrow this back. Use `helpers.DateTimeFilterSchema(...)` rather than an inline schema so every filter advertises both forms, and pass `helpers.EndOfDay()` to the binder for any *upper-bound* filter (`end_date`, `*_before`) — a date-only value there must resolve to the day's last second, or the range silently drops its closing day. Handlers that forward the value as a raw query-string parameter instead of binding it use `helpers.NormalizeDateTime(...)`.
- **A date filter's boundary rule is not guessable — read the endpoint, then say it in the parameter's own description.** A response says nothing about whether the boundary moment matched, so a caller that is not told brackets the window and re-filters the rows by hand. Put it on the parameter rather than only the tool: a model reading one filter never sees another's text. The rules are not uniform even inside a single tool — on `list_tasks`, `created_*` and `completed_*` are inclusive while `updated_*` is exclusive; on `list_allocations`, `updated_after` is exclusive and `deleted_after` inclusive. Two shapes cost more than a word:
  - **A bound whose rule depends on another bound.** `due_after` and `due_before` on `list_tasks` are each exclusive alone, but setting both switches the endpoint to an inclusive range — so adding a lower bound silently puts the upper boundary day back into the results. A task with no due date of its own is matched on its milestone's.
  - **Bounds that are not symmetric.** `list_calendar_events` reads both `started_after_date` and `ended_before_date` as the midnight that opens the named day, then compares the first against the event's start and the second against its end, so that day is included by one bound and excluded by the other: `started_after_date=2026-08-01` with `ended_before_date=2026-08-31` returns nothing from 31 August.

  `helpers.EndOfDay()` changes what the server is sent, not what the endpoint does with it, so it never substitutes for stating the rule. Setting a filter may also narrow the result set on its own — `completed_after`/`completed_before` restrict `list_tasks` to completed tasks whatever `show_completed` says — and that belongs in the description too. The same rule belongs on the matching twapi-go-sdk filter field, which is where a second server built on `pkg/` reads it.
- A v3 list endpoint may **default its own filters**, and an unfiltered call is then not an exhaustive one. `GET /projects/api/v3/allocations.json` answers a request carrying neither `startDate` nor `endDate` with today through 30 days from today, and the response says nothing about the range having been narrowed — so "all allocations on this project" silently comes back as one month. Do not paper over it by defaulting the window in the handler: that reorders results for every existing caller. Say it in the tool description instead, in the imperative, and pin the omission on the query string (`TestAllocationListWindowIsNotDefaultedLocally`). When wiring a new list tool, check the endpoint for filters that carry a default before writing "omit to get everything".
- Some endpoints serve a **different response shape per API minor version**, selected by the `Teamwork-Version` request header. The allocations endpoints render `projectId`, `assignedUserID`, `createdBy`, `updatedBy` and `deletedBy` as bare identifiers by default and as relationship objects under a later version. Neither this repo nor the SDK sends that header anywhere, so model the default shape — and do not start sending it, because it is a request-wide switch that would move the shape of every other endpoint at the same time.
- `twapi.HexColor` requires a leading `#` (`^#([0-9a-f]{6})$`) and rejects anything else at unmarshal time. An endpoint that returns six bare hex digits — the allocations endpoints return the colour without one — needs a plain `string` on the model, or every row fails to decode. Check what the endpoint actually returns before reaching for the typed colour.
- The calendar events endpoint binds `fields[calendarsEvents]`, not `fields[events]` (SDK v1.20.8+ sends the right key via a `sparsefields:key` marker), and its server-side filtering was broken until an API fix in 2026-08. Verify against the live API before assuming an endpoint honours `fields[...]`.
- `list_*` tools follow a specific contract — see `TaskList` in `internal/twprojects/tasks.go` as the canonical pattern:
  - Expose a `verbose` parameter (default `true`) via `helpers.VerboseSchema()`.
  - Execute the request with `twapi.ExecuteRaw(ctx, engine, req)` and stream the body straight to the caller, instead of decoding into the typed `*XxxListResponse` (avoids re-marshalling and preserves any fields the SDK struct doesn't model).
  - Expose a `fields` parameter via `helpers.FieldsSchema[projects.<Entity>]("<entity>")` whenever the SDK request has a `Filters.Fields.<Entity>` slot, parsed with `helpers.OptionalFieldsParam[projects.<Entity>](&req.Filters.Fields.<Entity>, "fields")`. It lets the caller name the attributes it wants instead of choosing between everything and `id` plus a label. Pass the same entity type to both: accepted values are reflected from that struct's JSON attributes, and `FieldsSchema` publishes them as the item schema's enum. The enum is required — it is the only place the model can read the names (tool definitions carry no output schema), so without it callers guess and get rejected. Cost: ~1,500 o200k tokens over 43 tools, +3.1% of the tool-definitions block (`go run ./cmd/mcp-tokens -base=main`), mostly cache-absorbed. With the enum in place the SDK validates unknown names before the handler runs; `OptionalFieldsParam` still rejects them for clients that skip validation, and always appends `id` (rows need it to be addressable by a follow-up `get_*`, and `WebLinker` needs it to attach a web link). Do not expose the sideload slots (`Fields.CustomFields`, `Fields.Projects`, …): they multiply the surface with entities the caller did not ask about. `summarize_timelogs` is deliberately excluded — its `Fields` slots feed an aggregate it computes itself, and its output schema is strict.
  - Do not dedup the enums between a `get_*`/`list_*` pair with `$defs`/`$ref`: each tool publishes its own `inputSchema` document, so a `$ref` would point outside it and the protocol has no shared root. Within one tool the enum appears once, so `$defs` saves nothing.
  - When `fields` is supplied it wins over `verbose`, and no sideloads are requested: sideloading would hand back the bulk the selection exists to avoid. Guard the `verbose` defaults with `len(req.Filters.Fields.<Entity>) == 0` (or a leading `switch` case) so neither branch overwrites an explicit selection. `TestSparseFields*` in `internal/twprojects/tools_sparse_fields_test.go` covers every list and get tool from one table and fails when a tool declares `fields` without being listed there. `TestSparseFieldsSchemaEnumMatchesValidator` is the one that catches a schema wired to a different entity than its validator.
  - Dropping the sideloads must not drop a filter an attribute *depends on*. `predecessors` is empty unless the request also sets `Filters.IncludeRelatedTasks`, and the API says nothing about the omission — so a selection naming it returned `"predecessors": []` on every row, indistinguishable from a task nothing blocks, which is how dependency questions came back "nothing is blocking". `list_tasks` had it only in the `verbose` branch and `get_task` cleared it with `Filters = projects.TaskRequestFilters{}`; both now set it through `taskFieldsNeedRelatedTasks(fields)`, which covers `predecessors` and `subTaskIds` alike. `IncludeRelatedTasks` is not a sideload — it adds no entity to the response — so honouring it alongside a selection returns nothing the caller did not ask for. When adding `fields` to a tool, check whether any attribute in the enum is gated on a request filter like this. `TestSparseFieldsPredecessorsCarryRelatedTasks` and `TestTaskSparseFieldsSubTaskIDsCarryRelatedTasks` pin both tools, on the query string, because the mocks reply with the same body either way.
  - A filter that gates an attribute may itself be gated. `includeRelatedTasks` reports **active** subtasks, dependencies and predecessors only, so a parent whose subtasks are all complete answers with an empty `subTaskIds` — indistinguishable from a task that never had any. `includeCompletedPredecessors` is what widens it, and despite the name it widens the whole related-task response rather than the predecessors alone. Where it belongs depends on whether the tool already lets the caller say what it wants to see. `list_tasks` does, so it hangs off `show_completed` with the other two completed-work filters — a caller that asked to hide completed work would not expect completed IDs in `subTaskIds`. `get_task` does not, and adding a parameter there would be noise: the endpoint addresses one task by ID, the flag only adds IDs, and the subtasks of the task you asked for are the answer to the question. So the get sends it unconditionally. Do not reach for `includeCompletedTasks` on a get — it changes nothing there. `TestTaskGetCarriesCompletedWork` and `TestTaskListShowCompletedReachesTheWire` pin the two halves.
  - Say the default exclusion in the tool *description*, not only in the parameter's. A list whose rows are filtered away by a default answers zero rows, which reads as "no such thing" rather than "already done" — a model that never saw the flag has nothing to retry with. `list_tasks` (`show_completed`) and `search` (`include_completed_items`) both spell it out.
  - When `verbose=false`: set sparse fields on `req.Filters.Fields.<Entity>` to a minimal set (typically `id` + name/title) and skip any hardcoded `Filters.Include` sideloads.
  - When `verbose=true`: include sideloads and the full field set.
  - Wrap the published output schema with `helpers.WithOptionalFields(...)` at the `OutputSchema:` line, not in the `init()` block: the schema vars are shared with `WithMetaWebLinkSchema` and the relaxation belongs to the tool that can return a sparse body. This clears every nested `required` array so sparse responses returned when `verbose=false` still validate. `StructuredContent` is always populated in both modes. It also nils every `additionalProperties`, so the value shape of an SDK `map[string]any` (a search hit's `meta`) has to go in the property's `description` — see `withSearchHighlightsSchema`.
  - OpenAI strict-mode caveat: because a sparse response returns a subset of fields, these output schemas cannot satisfy OpenAI's strict structured-output mode (which requires every property to be `required` and forbids `additionalProperties`). Clients must run with strict mode disabled.
- A `list_*` tool that takes `search_term` and comes back with an empty array attaches near-miss `suggestions` — see `internal/twprojects/suggestions.go`, wired into `TaskList`, `ProjectList` and `TasklistList`. An empty array alone gives the model no direction, and the name it searched for usually belongs to a different entity type ("Website Redesign" is a project, not a task), so it either guesses wrong or asks the user something the API could have answered. One extra `/projects/api/v3/search.json` call with the same term and *no* `type` filter returns hits of every type, each reporting its own; up to five nameable ones are attached as `{type, id, name}`. Rules the wiring depends on:
  - It runs **after** `helpers.WebLinker`. The linker stamps every top-level array with a link built from the calling tool's own path prefix, so a suggestion added before it sends a project candidate to `/app/tasks/123`. `TestListSuggestionsCarryNoWebLink` catches that — note its control half: the projects mocks leave the customer URL out of the context, and without it `WebLinker` returns the body untouched and any assertion about linking passes whatever the order.
  - An empty result with suggestions is not an error, and a term under three characters (the endpoint's floor, answered with a 400) skips the lookup and returns the response as it stands. A search that fails, though, is reported like any other API failure — through `helpers.HandleAPIError`, as an `IsError` tool result — rather than swallowed, so an empty list without suggestions always means the lookup ran and found nothing, never that it silently failed. `TestListSuggestionsSearchFailureIsAnError` pins this for every wired tool.
  - The lookup sets `includeCompletedItems=true` rather than inheriting the caller's `show_completed`. "It exists but it is finished" explains an empty result as well as "it is a different kind of record" does, and it is the explanation the caller's own filters just hid. Two consequences: a suggestion can name the same type the caller listed (`TestListSuggestionsCanNameTheListedType`), and it says nothing about completion — the output-schema description has to keep telling the model to read the record with the entity's own `get_*` tool. `SearchRequestFilters` also declares `IncludeArchivedProjects`, `IncludeTentativeProjects` and `IncludeArchivedMessages`, but twapi-go-sdk v1.21.4's `apply` never writes them to the query, so an archived project matching the term cannot be surfaced through this path until the SDK is fixed.
  - No prose goes in the JSON — the model narrates. The `suggestions` shape is published on the list tool's output schema via `withSuggestionsSchema` at the `OutputSchema:` line, not in `init()`: the schema var is shared with the matching `get_*` tool, which never returns suggestions. Cost is ~138 o200k tokens per tool, on the output schema only — `cmd/mcp-tokens` counts name, description and input schema, so it reports a 0 delta for this and is not evidence of no cost.
  - An absent list key is not an empty result. `withNearMissSuggestions` requires the key to be present and empty, because the mocks reply `{}` for everything: treating that as empty would fire a second request on nearly every existing test and make the search URL the "last URL" the `...WithRequestURL` mocks captured, breaking the query-string assertions of unrelated tools.
  - `suggestionEntities` is the single source of truth — sideload section, reported type name, requested sparse fields and label extraction in one entry, with the include list, field set and lookup map derived in `init()`. Comments and timelogs are deliberately absent: neither has a name (the search sideloads a comment's body and a timelog's description as their label), so neither answers "the thing you searched for is actually a …".
- `get_*` tools whose SDK request has a `Fields <Entity>GetFields` slot expose the same `fields` parameter — see `TaskGet` in `internal/twprojects/tasks.go`:
  - The slot lives on the request root (`req.Fields.<Entity>`), not under `Filters`, so it is `helpers.OptionalFieldsParam[projects.<Entity>](&req.Fields.<Entity>, "fields")`. The schema side is the same `helpers.FieldsSchema[projects.<Entity>]("<entity>")` as the list tool.
  - A selection must be answered with `helpers.NewRawToolResult(...)` rather than the tool's usual `projects.<Entity>Get(...)` plus `json.Marshal`. The SDK entity structs carry no `omitempty`, so re-marshalling the typed response emits every attribute the caller excluded as a zero value — `"dueDate": null` is indistinguishable from a task with no due date. Reset `req.Filters` on that path too, to drop the sideloads the handler requests by default. `TestSparseFieldsGetOmitsUnselectedAttributes` and `TestSparseFieldsGetDropsSideloads` pin both halves.
  - The unselected path is left alone: it still returns the typed round-trip, so existing callers see no change.
  - Wrapping the output schema with `helpers.WithOptionalFields(...)` is required here too, which is why `get_*` schemas are no longer strict. Sparse fieldsets on single entities arrived in twapi-go-sdk v1.20.7; before that, `get_*` could not return a subset and stayed strict-compatible.
- Ordering on a v3 list tool goes through the `ordering` type in `internal/twprojects/ordering.go`, the projects counterpart of twdesk's `setPagination`. It binds typed SDK filters rather than writing a `url.Values`, because every v3 list request models ordering as `Filters.OrderBy` plus `Filters.OrderMode`.
  - A tool declares its vocabulary once as an `ordering` var; `orderBySchema()` publishes it as the `order_by` enum and `param(&req.Filters.OrderBy, &req.Filters.OrderMode)` enforces the same slice in the handler. Do not hand-write an `Enum: []any{...}` literal beside a separate `helpers.RestrictValues(...)` list — the two drift, and a schema advertising a value the handler rejects is worse than no enum, since the client spends a call finding out. The enum itself is not optional: tool definitions carry no output schema and the SDK's `<Entity>OrderBy` values are Go constants the model never sees, so it is the only place the vocabulary is published. `order_mode` is `orderModeSchema()` / `orderModeParam(...)`; job roles, skills and custom item fields accept a direction but no order-by field.
  - Nothing is defaulted. Each endpoint documents its own default ordering (tasks by due date, activities by date) and the SDK's `querySetString` omits an empty value, so an unset filter sends no parameter and the API's default stands. Defaulting the way `setPagination` does for Desk would silently reorder every existing caller's results. `TestOrderingOmittedKeepsTheExistingOrder` pins this — including the exception, `NewTasklistBudgetListRequest`, whose constructor pre-fills `dateCreated`/`asc`: binding must not clear a filter the caller never mentioned.
  - A field-valued order-by needs its companion id parameter or the API ignores the sort: `order_by_custom_field_id` on tasks/projects/companies, `order_by_field_id` on custom item records (`orderByFieldIDSchema`). Check for an `OrderByCustomFieldID`/`OrderByFieldID` filter whenever a vocabulary contains `customfield` or `customitemfield`.
  - Assert ordering on the query string, never the response — the mocks reply with the same canned body either way. `TestOrderingEveryPublishedValueReachesTheWire` in `internal/twprojects/ordering_test.go` drives every published value of every tool from one table and fails when a tool declares ordering without a row. Two traps it encodes: the team routes are v1, so the SDK renames the parameters to `sortBy`/`sortOrder`; and `list_custom_item_records` resolves the item's field schema *after* listing, so `testutil.ProjectsMCPServerMockWithRequestURL` hands back the follow-up request and the ordering looks missing — use `ProjectsMCPServerMockWithRequestURLs`, which captures every request, for any tool that makes more than one call.
  - Cost: ~2,100 o200k tokens across 25 tools, +4.3% of the tool-definitions block (`go run ./cmd/mcp-tokens -base=main`), concentrated in the large vocabularies (`list_tasks` publishes 34 values).
- An enum-valued *filter* goes through the `vocabulary` type in `internal/twprojects/vocabulary.go`, the filtering counterpart of `ordering` and for the same reason: `arraySchema()` publishes the enum and `listParam(...)` enforces the same slice in the handler, so a tool cannot advertise a value its handler rejects. Take the values from the SDK constants. `newVocabulary` is for filters whose published names *are* the wire values (`project_statuses`); `newNamedVocabulary` maps names onto something else, which is what a numeric enum needs — project health is an integer whose meaning is positional (1 is bad, 3 is good) and no tool definition would tell a model that, so the tool publishes `good`/`ok`/`bad`/`not_set`. Watch for a zero-valued member (`not_set` is 0): it survives the SDK's `querySetInt64s`, which drops empty *lists* but keeps zero *elements*, unlike the scalar `querySetInt64`.
- `twprojects-search` carries two type-shaped parameters and they do different jobs. `types` is the filter: it maps to the endpoint's `types` query parameter and decides which records are *found*. `sideload` (the `include` query parameter) only decides which of the found records are expanded under `included` — a hit whose type it leaves out comes back as a bare `{id, type}` pair with no name. That parameter used to be called `include` and described as "entity types … narrow it to the types of interest", which reads as a filter with no filter available: models narrowed it, got hits of other types back as nameless stubs, and stopped calling search for the rest of the conversation. Keep each description off the other's job, and keep the tool description off entity types no parameter accepts — `files` and `calendarevents` can be filtered on but not sideloaded, so the vocabulary publishes neither. The SDK's singular `Filters.Type` sent `type`, which the endpoint does not read at all, so it never filtered anything; it is `Filters.Types` now, comma-separated. `TestSearchTypesFilterReachesTheWire` pins the query string, since the mocks answer the same body either way.
- **A sideload selector is a parameter of last resort, and it is named `sideload`, never `include`.** Almost no tool should expose one: every list and get tool sets `Filters.Include` itself, and the allocation tools show the alternative — `include_financial_details` is a boolean naming the *intent*, which the handler turns into a sideload list. Expose the raw list only when the caller genuinely picks among unrelated entities, as `twprojects-search` does across twelve. The name matters because `include_*` is already taken by something else: ten parameters (`include_completed_items`, `include_highlights`, `include_archived`, `include_tentative`, `include_financial_details`, …) are booleans that widen what the response *covers*, so a list-valued `include` sitting in that namespace reads as a filter — which is how search's sideload parameter came to be used as one. Whatever it is called, its description says it never changes which records are found, and names the parameter that does.
- `list_projects` answers "my projects" through `user_ids` (the endpoint's explicit-membership filter, so the model needs an ID from `twprojects-get_user_me` first) or `only_starred`, and refines it with `hide_observed` and `only_admin_access`. Lateness is only reachable as a filter: a project row's `status` attribute is the storage state (`active`, `archived`, `deleted`), never the schedule, so `project_statuses=["late"]` is the sole way to ask which projects have slipped, and nothing in a response can be post-filtered to the same answer. Every one of these is a filter rather than row shaping, so `count_projects` inherits them and "how many of my projects are late" is one call.
- Counting is a mode of the `list_*` tools, not a second implementation. A list tool whose v3 endpoint reports `meta.page.count` — in SDK terms, whose request filters carry a `CountMode` slot — exposes `count_only` via `helpers.CountOnlySchema("<entities>")`, binds it with a plain `helpers.OptionalParam(&countOnly, "count_only")`, publishes the alternative body with `helpers.WithCountOnlySchema(...)` around the `WithOptionalFields(...)` at the `OutputSchema:` line, and answers it with one branch: `if countOnly { return helpers.NewCountToolResult(ctx, engine, req, "failed to count …") }`. Put that branch where every *filter* is set but before the row shaping (`list_tasks` sits after the `show_completed` mapping and before the `fields`/sideload `switch`, so the count query carries no `includeRelatedTasks`). `NewCountToolResult` rewires the request itself, by reflection over the slots every v3 list request shares (`Filters.Page`, `Filters.PageSize`, `Filters.CountMode`, clearing `Filters.Include` and `Filters.Fields`), so a new list tool needs no per-entity count code; a request missing a slot is reported, never sent as-is.
  - Pinning `twapi.ListCountModeExact` is load-bearing, not an optimisation. `skipCounts=true` does not remove `count` from the response — it replaces the total with the lower bound `(page * pageSize) + 1`, which at `pageSize=1` is 2 for any non-empty result — and the SDK's `ResolveCount` only clears that for callers who decode the typed response, which list tools deliberately do not. Four endpoints (custom items, custom item fields, custom item records, time reports) default to skipping, so inheriting the endpoint default would answer those with a 2. `TestCountOnlyAsksForAnExactCount` asserts `skipCounts=false&page=1&pageSize=1` on the query string for every tool in `countOnlyToolCases`, because the mocks reply with the same body either way. `TestCountOnlyToolsAreCovered` fails when a tool declares `count_only` without a row; the table's comment lists the endpoints that cannot answer a count (cursor-paginated, v1, unpaginated, no `SetRequest`) and why.
  - A missing `meta.page.count` is an error result, never a zero: a zero reads as "nothing matches", which is exactly the wrong answer to the question being asked.
- A `count_*` tool is derived from its list tool, never written twice. `countTool(TaskList(engine), MethodTaskCount, …)` in `internal/twprojects/count.go` copies the list tool's input schema minus the row parameters (`page`, `page_size`, `cursor`, `limit`, `verbose`, `fields`, `count_only`, and the four ordering parameters) and calls the list handler with `count_only` injected past validation, so the filters, their binding and the endpoint they resolve to stay defined once. It returns the `count_only` body unchanged — a strict `{"count": N}`, so the two ways to reach a count are indistinguishable once answered — after checking a count is actually there, which is what stops a broken delegation from passing rows back under a schema that promises a number. Both surfaces ship because they are reached from opposite ends — `count_only` catches a model already in a list call path, `count_tasks` a model reasoning from "how many" — and a prompt rule telling weaker models to pass a flag is not a structural guarantee. Adding one for another entity is a one-line registration; weigh it against the tool-definition cost first (`count_only` across 27 list tools plus the four count tools measured +7.6% with `go run ./cmd/mcp-tokens -base=main`, over half of it in the count tools inheriting a whole filter surface each — `count_tasks` alone is 1,189 tokens). `countToolDroppedParams` is what keeps that inheritance to filters: ordering is row shaping, so a new ordering parameter belongs in that list, and `TestOrderingToolsAreCovered` fails when one leaks into a count tool. `mcp-tokens` counts input schemas only, so an output-schema change — the `WithCountOnlySchema` half of this one — reads as +0 there and still costs a client tokens on `tools/list`.
- Run `go test ./internal/twprojects` until green.
- `docs/tool-reference.md` (Markdown) and `docs/index.html` (the GitHub Pages site) are both generated by `cmd/docs-gen` and guarded by `go test`; ordinary tool add/remove/rename is caught automatically (regenerate with `go run ./cmd/docs-gen`), but two changes need a manual edit to `cmd/docs-gen/main.go`: flipping `allowDelete` to `true` on a shipped server, or adding a new product package (register it in `products()`). The two documents share `classifyToolset`, so a tool cannot land in one's matrix and the other's other-actions list.
- The HTML page is committed, not built in CI: `.github/workflows/pages.yaml` serves the file as-is, because the golden test already guarantees it is current. It must therefore stay deterministic — no timestamps, no map iteration (`TestGeneratedHTMLIsDeterministic`). Its brand assets in `cmd/docs-gen/assets` are the official Teamwork.com logo files, embedded verbatim; the [brand guidelines](https://www.teamwork.com/brand/) forbid redrawing or restyling the lockup, and reserve pink for accents rather than buttons or large blocks of text. See `cmd/docs-gen/README.md`.

## MCP SDK upgrades and protocol compatibility
- The SDK (`github.com/modelcontextprotocol/go-sdk`) keeps its Go API stable but does change wire behaviour between minor versions. Read `docs/mcpgodebug.md` in the module cache (`$(go env GOMODCACHE)/github.com/modelcontextprotocol/go-sdk@<version>/docs/mcpgodebug.md`) before and after any bump: it lists every behaviour change and the `MCPGODEBUG=<param>=1` escape hatch that restores the old behaviour. Escape hatches are removed two minor versions later, so they are stopgaps, never permanent settings.
- Old clients must keep working. When the SDK adds a protocol method that replaces an older one, support both: `server/discover` (SEP-2575) and `initialize` are both in `auth.methodsWhitelist` for exactly this reason. Never remove a legacy entry from that whitelist.
- `pkg/request.ResponseWriter` must keep its `Flush()` and `Unwrap()` methods. The SDK writes Server-Sent Events through `http.ResponseController`, which resolves the flusher by unwrapping — every streamable HTTP response on `/` is an SSE stream. Without them flushing silently degrades to a no-op and streaming clients hang. It also caps the body it captures for logging, because SSE streams live as long as the request.
- Cacheable results (SEP-2549: `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read`, `server/discover`) default to `cacheScope: "public"`. Anything whose content varies per token — `tools/list` is filtered by OAuth scope — must be set to `cacheScopePrivate` in the receiving middleware in `pkg/config/config.go`, or a shared proxy can serve one tenant's response to another.
- Do not advertise capabilities the server does not honour. `logging` is deliberately omitted, and the `listChanged` flags are deliberately false: advertising them invites clients to open a long-lived `subscriptions/listen` stream that a stateless, load-balanced deployment would hold open with nothing to send. `TestCapabilitiesOmitLogging` and `TestCapabilitiesOmitListChanged` guard this.
- Do not add a manual keepalive ping loop. `mcp.ServerOptions.KeepAlive` in `config.NewMCPServer` already drives pings. In `cmd/mcp-stdio` a hand-rolled loop is actively harmful: on failure it has no request to reply to, so the error is written onto stdout, which is the protocol stream.
- Keepalive pings are gated on the negotiated protocol version by `keepalivePingGate` in `pkg/config/config.go`, a *sending* middleware. `ping` was removed in `2026-07-28` (SEP-2577) — the SDK's own server refuses an inbound one on such a connection — but `KeepAlive` starts the loop at connect time, before any version is known, and never revisits it, so the decision cannot live in `ServerOptions`. The gate answers `ping` with `CodeMethodNotFound`, which is what the loop reads as "peer does not support ping": it stops pinging and leaves the session open. Do not return any other error there — anything else counts as a failed ping and eventually closes the session. Reaching `2026-07-28` needs the SEP-2575 per-request `_meta` path (`io.modelcontextprotocol/protocolVersion`); `initialize` is deprecated in that version, so the SDK caps that handshake at `2025-11-25` no matter what the client asks for. `TestKeepalivePingGate*` in `pkg/config/config_keepalive_test.go` pins both halves with a hand-rolled client, since `mcp.Client` picks its own version.
- `KeepAliveFailureThreshold` is set to 3. Left unset it is 1, so a single unanswered ping closes the session — at 30s plus the 15s ping timeout, a client that merely ignores pings loses its session (and with STDIO, the process exits). The spec expects multiple failures before a connection is considered dead; misses below the threshold are still logged.
- Pin limits the SDK also enforces. `mcp.StreamableHTTPOptions.MaxRequestBodyBytes` is set explicitly in `cmd/mcp-http/main.go`; left at zero the SDK applies its own default (4 MiB), silently tightening the limit `limitBodyMiddleware` advertises.
- Client-visible protocol changes belong in the "Protocol Compatibility" section of `cmd/mcp-http/README.md`.

## Security considerations for agents
- Never print or commit bearer tokens. Use env vars only. Redact tokens in logs.
- Prefer running the STDIO server with `-read-only` by default during development.
- For HTTP deployments, ensure TLS, least-privilege tokens, and sensible log levels.
- Be careful with delete operations; keep them gated behind `allowDelete`.
- `twprojects-create_file` uploads in two steps: the API reserves space, then the SDK PUTs the bytes to a pre-signed storage URL via `Engine.Do`. That second request rides the same client, so every middleware sees it, and it must be left alone. `presigned.IsURL` gates the HAProxy rewrite (the signature covers the host), the TLS split in `network.PresignedSplitTransport` (storage's certificate is genuine, unlike HAProxy's), and body logging in `LoggingRoundTripper` (the body is the customer's file, and its content type is the file's own, so `text/markdown` looks loggable). The URL is itself a credential, so `presigned.RedactSignatures` — which `logsafe` composes into its own scrubbing — strips the signature params wherever they appear, including the JSON body that carried the URL.

## PR/commit guidance
- Before commit: `gofmt -s -w .` (or run your editor’s Go format), `go vet ./...`, `go test ./...`.
- Include or update tests for any tool behavior changes.
- Keep `README.md` end-user focused; put agent-oriented details here.
- A pull-request title needs one of the prefixes CONTRIBUTING.md lists, and it is load-bearing twice over: the `PR lint` workflow rejects a title without one, and `cmd/next-version` reads it to pick the release bump (`Feature:` → minor, everything else → patch, `Feature!:` or a `BREAKING CHANGE:` body → major). The *title* is what counts, not the commits: `cmd/next-version` resolves each commit to its merged pull request and folds a rebase-merged branch into one change, so an unprefixed `Fix comment` inside a `Feature:` pull request is harmless while an unprefixed title silently costs the release its minor bump — which is how v1.27.4, v1.28.1 and v1.28.3 each shipped a feature under a patch tag.
- `.github/workflows/pr_lint.yaml` enforces the prefix by running `go run ./cmd/next-version -check-title="$PR_TITLE"`, not a third-party action: the vocabulary is `bumpByPrefix` itself, so the door and the release cannot disagree, and the repo's Actions policy (`Teamwork/mcp` allows only Teamwork-owned, GitHub-created or Marketplace-verified actions plus an explicit pattern list) needs no new entry. `amannn/action-semantic-pull-request` was the first attempt and was rejected by that policy. Two consequences to preserve: the title reaches the script through `env:`, never `${{ }}` interpolation — it is attacker-controlled text on a fork's pull request — and `checkTitle` validates the prefix against `bumpByPrefix` directly rather than through `classify`, which reports a major for *any* prefix carrying a `!` so that a breaking change is never under-versioned. That leniency is right when reading history and wrong at the door: `Whatever!: …` must not pass. `TestCheckTitle` pins both halves.
- The prefixes CONTRIBUTING.md documents are guarded by `TestEveryContributingPrefixIsMapped`, which parses the `` - `Xxx:` for `` list and asserts each one is both mapped and accepted by the check — keep that list's shape. `acceptedPrefixes()` builds the rejection help from `bumpByPrefix` so the guidance an author gets cannot drift from what is accepted (`TestAcceptedPrefixesHelpIsComplete`). `.github/dependabot.yml` pins `commit-message.prefix` so its titles keep passing; without it Dependabot infers the prefix from recent history.
- Releasing is `workflow_dispatch` on `.github/workflows/release.yaml` with `bump` (auto/patch/minor/major) and `dry_run` inputs; pushing a `v*.*.*` tag by hand still works and skips the computation. The two entry points meet in the `version` job, whose outputs (`version`, `previous_tag`, `sha`, `release`) every other job reads — do not reintroduce `GITHUB_REF`-derived versions downstream, and check out `needs.version.outputs.sha` rather than `github.ref`, which on a dispatch is a branch. The dispatch path cannot create the tag and let the push path take over: a tag created with `GITHUB_TOKEN` does not trigger `on: push: tags`, so it would tag and release nothing. `dry_run` works by setting `release=false`, which every downstream `if` reads.
- `cmd/next-version` skips the commits the release process itself lands on `main` (`tw-mcp vX.Y.Z`, the Homebrew formula update) via `releaseChorePatterns`. That formula pull request merges *after* the tag it belongs to, so it always falls inside the next release's range; without the skip every release would report an unclassified change. It also refuses to compute a version that is already tagged, and errors rather than reporting a release with no changes.
